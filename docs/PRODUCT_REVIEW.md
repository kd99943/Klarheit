# Klarheit 产品评审与试运营方案

2026 年 11 月 22 日 · 扩展版

## 建议先做的三件事

1. **把可售范围定下来。** 确定谁供货、谁能配、卖哪些镜框和镜片、送到哪里、如何处理退款和重做。让商品页的承诺有对应的价格、产能和承接人。
2. **完成一副眼镜的订单闭环。** 让用户能确认实物规格、可配性、总价与交期。让运营能处理处方补充、缺货、支付不明、制作延期、物流异常与售后，并让用户从订单里查到进度。
3. **用受控试单决定是否加量。** 先通过异常演练，再做真实小额交易和少量完整交付。用按期交付、支付对账、售后积压与单单贡献判断能否扩大流量。

当前工作区已有目录、WebAR、配镜、购物车、支付、发货和退款的实现基础。最紧迫的问题分散在功能之间。例如，从试戴进入配镜时，找不到原款会回退到目录第一项。首页同时出现「10 个工作日内发货」和「10 个工作日含配送」，确认邮件写预计 14 个工作日送达。客服和加工方也需要有地方接住这些交接异常。 [配镜页](../front_end/src/pages/ConfigLab.tsx) · [首页承诺](../front_end/src/i18n/locales/zh/landing.json) · [确认邮件](../backend/src/main/java/com/klarheit/backend/email/EmailService.java)

## 1. 首发定位与经营选择

| 首发方案 | 用户能得到什么 | 启动条件与建议 |
| --- | --- | --- |
| 验配合作方已就绪 | 已有验光结果的用户在线购买一副单光眼镜，可以先试戴，也可以直接选框配镜。 | 推荐作为首发假设。由验配方确认可加工范围、镜框与镜片组合、复核时限、质检标准及重做责任。优先限定一个配送区域、少量可稳定供货的款色、一条真实支付通道。 |
| 镜架可供货，验配能力尚缺 | 用户线上选购镜架，售前清楚看到镜架规格、配送和售后服务。 | 适合作为独立的降级方案。要先增加镜架独立报价、结算和售后规则。当前订单接口要求提交镜片与处方，需先调整这条路径。 |
| 供货、验配或售后暂未落实 | 用户可浏览和试戴，了解配镜所需资料，并自愿留下咨询意向。 | 适合作为验证需求的阶段。咨询入口只收接洽所需信息，待专人接手后再确定资料收集方式。 |

首发用户假设是**已有处方、希望换框或添置备用眼镜**的人。无处方用户可浏览、试戴、保存和咨询。对儿童、渐进镜片、复杂处方、跨境及线下预约，先由验配和运营确认可服务能力，再决定是否接受订单。试戴和服饰风格是获客假设，可否改善购买决策要从用户任务完成情况观察。

开始开发前，由项目负责人召集供货、验配、客服和财务确定下列业务输入。小团队可以一人承担多个职责，每类决定都要有能确认的人和替补。

| 决策 | 需要定下的内容 | 确认人 |
| --- | --- | --- |

| 供应方式与风险 | 哪些款自有库存，哪些由合作方确认。补货和报废由谁承担。每日可复核、加工、质检和发货的数量。 | 采购、验配 |
| 可配范围 | 允许的镜框、镜片和处方组合，由谁判定、何时判定、遇到不明确的资料如何联系用户。确定接单前应核验的资格和业务条件。 | 验配负责人 |
| 收款与售后 | 指定商户、对账人、人工退款审批权限。明确镜架、定制镜片、质量问题、延误、物流损坏等情况的受理标准和费用承担。确认发票或购买凭证由谁提供。 | 财务、客服 |
| 经营底线 | 拿到实际采购、加工、物流、手续费、售后和获客成本。确认每单可接受的最低贡献、试单预算和一周能处理的异常单量。 | 项目负责人、财务 |

## 2. 用户旅程与主要断点

P0 是接受真实订单前必须具备的能力，可以由有负责人的人工流程承接。P1 用于有试单证据的体验优化。P2 需要额外供应、渠道或运营能力。

| 用户场景 | 仓库现状与用户影响 | 建议 |
| --- | --- | --- |
| 首次访问，想知道能买什么、多久收到 | 目录支持筛选和搜索。商品模型有材质、形状、尺寸和图片，缺少可售规格、数量和供应状态。首页、结账和页脚有品牌、数据与合规表述，部分文案需要对应真实业务和证明。 | P0 在详情页把实拍、款色、尺码、适合的对照方法、价格范围、配送和售后说清楚。商品目录区分缺货、暂不可配和请求失败。 |
| 试戴外观后返回商品或配镜 | 可切换镜框、颜色和摄像头，也有截图操作。当前配镜页匹配不到款式可能默认第一项，估算瞳距已标注供选框参考。 | P0 固定款色交接和摄像头失败的继续路径。P1 用真机验证打开、跟踪稳定、切款与返回。 |
| 没有处方，或拿着看不懂的验光单 | 配镜工坊要求先登录。页面支持字段校验，首页对范围和镜片推荐已有表述。用户可能在注册后才发现缺资料或所需组合超出加工范围。 | P0 在登录前提供配镜所需资料、支持范围和价格预览。已知不支持与需人工核对分别给出下一步。P1 再验证延后登录能否提高完成率。 |
| 已配一半，换设备、登录过期，或帮家人配 | 购物车及结账草稿使用浏览器存储。已有读取最近一份处方的接口，账户处方卡仍显示占位，未见配置页沿用处方的入口。下单也会保存一份处方，因此接口返回的「最近」可能来自尚未付款的订单。 | P0 结账前明确核对佩戴人、处方来源与收件人，登入后恢复自己尚可继续的草稿。共用设备可清除资料。P1 根据实际需求增加多份处方与跨设备同步。 |
| 想买两副，或只买镜架 | 购物车可留多条配置，每次结账只选择一条。后端订单要求一件商品和一组镜片、处方字段。 | P0 在购物车和按钮上明示按副结算，支付后保留其他配置。镜架独立业务按首发方案另行决定。P1 再验证合单和不同佩戴人的需求。 |
| 已付款，但回跳、刷新或隔天查看 | 支付宝默认回到个人中心，订单页能查状态，未见用户继续支付和对应订单的通用恢复入口。确认页依赖导航状态，直接打开时信息有限。 | P0 创建订单后以订单号恢复。待支付、确认中、已付款、订单关闭各有文案与下一步，用户无需凭扣款截图猜测。 |
| 等待制作，想改地址、查物流或开票 | 后台可填写承运商与单号，已付款可直接发货。代码有已送达状态常量，未找到将普通订单推进到该状态的业务入口。收件人资料、售后联络和购买凭证缺少完整处理路径。 | P0 补复核、制作、质检与签收的业务记录，明确地址变更的截止点和财务答复。用户能看到目前负责人要做什么、自己要做什么。 |
| 到货不合适，想重做、维修或退换 | 首页对镜框和定制镜片写了不同承诺。代码可处理撤单退款，已发货订单无法走后台撤单，客户侧未见发货后的工单。 | P0 设置订单内售后表单，区分做错、破损、个人佩戴不适、镜架退换。由客服按规则分派验配或财务。 |

## 3. 用户侧 P0 需求

### 3.1 商品详情、试戴和款色交接

- **详情页主按钮随实际可售状态变化。** 可直接配镜时显示「选镜片和处方」。缺资料时提供所需材料。缺货或暂停销售时提供替代款或咨询。将镜框起价与有明确配置的配镜预估分开显示，购物车标记尚待选镜片的商品。
- **商品资料维护到可发货的规格。** 每个可售规格包含款号、颜色、尺码、实拍、尺寸解释、供货方式和与 AR 模型的映射。尺码帮助优先让用户对照自己的镜架标识，样品实测后再标注适配范围。仓库初始目录含钛、钢和板材款，首页的统一钛材表述应按对应实物款发布。
- **试戴围绕选框。** 开启摄像头前说明用途。拒绝、设备不支持、模型加载失败及权限到期时，保留当前款色并提供实拍和继续配镜。截图操作提供清除入口。离开页面时确认摄像头停止。虚拟尺寸和颜色给出与实物可能存在差异的提示。
- **验收。** 从目录、详情、试戴、历史链接和购物车分别进入配镜。两款镜架使用同名颜色时，五条路径均按商品和款色识别。款色下架或映射失效时保留能沿用的草稿、提示重选，并显示变更后的商品和价格。未授权摄像头的用户能直接通过实拍完成选框。

### 3.2 配镜引导和处方核对

1. 先让用户选择「已有处方」或「需要帮助」，展示一张虚构的填写示例。字段名称同时呈现通俗解释、单位、左右眼和正负号。需补充时指出具体字段、由谁确认以及如何继续。
2. 已有处方可录入或选取自己确认过的记录。付款前展示佩戴人、处方来源及录入或验光日期、左右眼摘要、所选镜片和总价。若首批支持不同佩戴人，先做清楚的选择和确认，再考虑长期管理家庭成员处方。
3. 可配性由验配方确认。每副先选一款基础镜片，再选择兼容的镀膜。前后端采用同一份规则，覆盖互斥选项、必选项和具体镜框的加工限制。将配置分成可下单、需人工确认和超出范围。可下单的初期也逐单复核。需人工确认的订单在用户同意可行方案及最新价格后进入支付。已付款后发现资料不足时，暂停制作，给出补充期限、预计新交期和取消处理选项。
4. 一份处方记录用于该订单的验配。长期保存为可复用处方应有清楚的用户操作。修改历史处方时保留原订单对应版本。试戴产生的估算瞳距可以辅助选框，配镜提交以经确认的处方数据为准。
5. **验收。** 用合格处方、缺瞳距、左右眼错填、镜框和镜片组合不支持、提单后补资料分别走查。用户知道原因和下一步。复核意见、确认后的处方版本与订单一致，未复核订单不能开工。

首页目前提到「近一年内」、度数范围与按度数给出镜片建议。FAQ 列出的折射率是 1.56、1.61、1.67，仓库种子目录是 1.74 加两种镀膜。请验配方确认实际在售选项及适配范围，再统一 FAQ、配镜配置和加工单。 [首页规则](../front_end/src/i18n/locales/zh/landing.json) · [初始目录](../backend/src/main/resources/db/migration/V8__seed_catalog_data_and_fixes.sql) · [处方接口](../backend/src/main/java/com/klarheit/backend/prescription/PrescriptionController.java) · [下单与处方保存](../backend/src/main/java/com/klarheit/backend/order/OrderService.java)

### 3.3 报价、登录和支付恢复

- **报价。** 商品详情直买目前会预选 1.74 镜片，结账存在回退价及固定免运费展示。让用户明确确认镜片及附加收费，由服务端返回有效的完整报价。接口异常时保留配置并提供重试。使用优惠后再改镜片、规格或地址，要重新计算资格和金额。变动后显示差额并再次确认。
- **登录与地址。** 登录失败、短信收不到、手机号未绑定、邮箱填错、会话过期，分别提供可行的恢复方式。账户页当前固定显示「邮箱已验证」，修改密码和删除账号按钮未接实际处理。验证标记取真实状态，功能未实现时可提供人工处理入口。收件人与账号持有人可以不同，配送地址须满足首发区域与联系要求。弱网下迟到的默认地址不得覆盖用户已手填的收件资料。付款后按制作和发货节点由客服处理。
- **订单恢复。** 用户确认报价后创建一张订单，得到可重新打开的详情。未扣款可继续。支付确认中时提供刷新和稍后查看。已过期则解释重下，必要时复用配置并重新报价。网络超时、重复点击和两个页面重复操作最终能查到同一笔有效购买。支付宝回跳以订单信息和服务端确认状态为准。
- **验收。** 覆盖从游客进入登录再返回、价格与优惠变更、下单超时后重开、外部支付取消、支付后即时返回、过一段时间再查、订单超时和第二天在另一台设备打开。用户能看懂扣款状态、该操作是否可重复、订单是否仍可继续。购买一副后其他购物车条目保留。

### 3.4 移动体验、可访问性和数据处理

- 手机上能用同一只手走完选框、配镜和支付。测试底部按钮、软键盘、弹窗关闭后的焦点、错误字段定位、屏幕阅读器和纯键盘流程。款色选择同时提供可读名称及选中状态。核心购买步骤用用户所在市场的语言，价格和订单状态也按同一口径展示。
- 将摄像头画面、试戴截图、处方草稿、成交处方、联系方式和分析事件分别列清用途、保存位置、期限、访问权限和用户如何请求清理。当前购物车用固定浏览器存储键保存配镜数据，退出时需要清除或隔离处方和截图。游客购物车保留商品规格，登入前后由用户确认合并。清理草稿与处理历史订单应独立，覆盖退出后换账号、共用设备、恢复标签页与客服导出。
- 配镜校验事件目前携带输入原值，配置 GA4 时可随事件转发。移除原始值，用字段类别和错误码定位流程问题。复核含订单号的动态路径、搜索词和错误文本，以及诊断日志与通知中的个人数据。分析页面类别时使用路由模板。用户能在账号中找到数据处理信息和咨询入口。
- 页脚和结账当前出现 ISO 12870、瑞士数据隐私保护，首页还有正品证书和试戴贴合类文案。将每条公开承诺对应到可验证的材料或明确的服务能力，确认后再发布。遇到尚未落实的服务，页面提示现阶段用户能做的事。

## 4. 商家侧 P0 需求

### 4.1 供货、库存和结算

| 环节 | 首版规则与处理 |
| --- | --- |
| 上架和更新 | 每个款色尺码有独立编号、采购成本、供货来源、可售库存、质检样品和上架人。商品变更应能暂停可售或归档。区分停售、临时缺货和暂停配镜。先核对在售实物与照片、三维模型和加工参数。 |
| 库存与产能 | 订单进入待支付后按约定时限占用库存。付款确认后扣减，关单确认后释放。若付款无法确认，保留异常状态由值班人处理。无法提供实时库存的合作款先人工确认。对临期缺货和抽检不通过的批次建立停售与替代路径。试单限额同时考虑验配、加工、质检和客服产能。 |
| 价格和优惠 | 价格版本覆盖镜框、镜片、配送、优惠及币种。确认下单后保留成交快照、送达承诺和适用的售后政策版本。首版可只支持单券，写清适用范围、有效期、门槛、占用与释放规则，以及取消或退款后如何处理优惠。零元单、叠券与部分退款先由财务确认能力和政策。 |
| 地址与送达 | 付款前校验支持的地区、承运商和总价。地址簿编辑不覆盖历史订单。发货前改址由客服复核并记录，发货后改址走承运商和人工确认。把供应到货、验配、制作、质检和承运商时效纳入预计发货与送达区间。 |
| 收款与对账 | 先验收已有的支付宝通道。订单号、网关流水、金额、币种、支付时间、退款请求与结果可核对。每天把站内订单与商户账单逐笔比对，差额、超时、重复收款和退款滞留进待办，记录负责人和处理时限。退款受理、网关完成和用户到账提示各按已确认的信息展示。 |
| 购买凭证 | 订单详情提供成交明细和付款状态。确认是否支持开票、由谁收集必要字段、多久交付、退款后如何处理。试点期间可人工受理，用户可查询进度。 |

关键验收包括最后一件被两个用户同时结账、报价后变价、优惠额度耗尽、地址不在范围、订单付款超时、延迟收到支付确认、改了商品仍能看历史成交明细。每笔异常都有可追踪的待办，重复上报归到同一事项。旧单缺少历史字段时，按能追溯到的证据展示，避免将迁移时的目录值视作当时成交信息。 [结账价格与配送](../front_end/src/pages/Checkout.tsx) · [订单计价与快照](../backend/src/main/java/com/klarheit/backend/order/OrderService.java) · [历史快照回填](../backend/src/main/resources/db/migration/V22__preserve_order_catalog_snapshots.sql) · [优惠服务](../backend/src/main/java/com/klarheit/backend/coupon/CouponService.java) · [支付补偿任务](../backend/src/main/java/com/klarheit/backend/payment/PaymentReconciliationScheduler.java)

### 4.2 订单状态和责任交接

沿用现有订单号和交易记录。试运营可先在人控工作台补充复核、签收和售后状态，确保它们能追到同一订单，用户也能查看与当前事项有关的进度。

| 状态线 | 典型进度 | 主要责任人 |
| --- | --- | --- |
| 交易 | 待支付 → 支付确认中或已付款 → 申请退款、退款处理中、退款完成。未扣款关闭另记原因。 | 财务与支付值班 |
| 验配与履约 | 待核对 → 待用户补充或可制作 → 制作中 → 质检通过 → 已发货 → 已签收。缺货、延期、质检不通过、拒收和遗失可记录为异常。 | 验配、加工和发货 |
| 售后 | 已受理 → 待补资料或待收回检查 → 退款、维修、换货或重做处理中 → 结案。每次处理记录原因和下一次联系时间。 | 客服协调验配和财务 |

**关键交接。** 已付款且验配通过后可制作。质检通过且未被售后拦截才可发货。录入快递后形成通知和可查件信息，随后由承运商或运营写入签收时间。一个订单可以同时处于「已送达」和「售后重做中」。重做关联原订单、审核版本和新运单，便于核对承诺时间及成本。

**通知顺序。** 优先做付款确认、需要用户补料、确认延期、发货、售后受理和退款结果。订单页面保有完整进度。通知用实际可用的语言和渠道，发送失败进入运营待办。现有确认邮件可降级为本地预览，预览与真实送达分别验收。 [订单状态](../backend/src/main/java/com/klarheit/backend/order/OrderStatus.java) · [后台订单操作](../backend/src/main/java/com/klarheit/backend/order/AdminController.java) · [通知实现](../backend/src/main/java/com/klarheit/backend/email/EmailService.java)

### 4.3 取消、退换和重做

首批发布前，由客服、财务和验配负责人为每类情况确认申请期限、服务范围、责任划分、费用与退款时限。将决定同步到商品页、付款前的订单确认和客服操作说明。以下是建议的处理路径。

| 情形 | 用户怎么走 | 后台怎么处理 |
| --- | --- | --- |
| 未付或支付确认中想取消 | 在订单查看是否可取消。支付确认中提示当前正在核实，并告知后续渠道。 | 可关闭的单先确认关单，再释放库存和优惠。晚到款交财务核对及退款。 |
| 已付、未开始制作 | 从订单发起取消或改址，看到处理进度。 | 客服确认是否已开始加工，核对金额、地址变更和优惠释放，按已公开规则处理并记录。 |
| 制作中或预计超期 | 收到新的发货、送达时间及进一步选择。 | 先确认能否停止或修改加工，记录新增成本和负责人。对不能按原承诺履约的单，由客服主动提供下一步。 |
| 收到错配、破损或疑似质量问题 | 提交原因和必要信息，查询处理进度和下一次联系时间。 | 识别发错货、运输损坏、加工或质检问题。联系验配或物流，记录取回要求、运费、退款或重做的决定。 |
| 物流显示签收但用户未收到 | 从原订单提交未收到，查看下一次反馈时间。 | 查承运商签收信息和最后投递环节，复核地址，按确认结果联系用户并处理补发或退款。 |
| 佩戴不适、尺码不合适或改变主意 | 根据订单类型看到不同的支持路径，例如调整咨询、镜架退换或验配复核。 | 确认原订单版本、镜框和镜片，按已发布规则给出处理方式。需要重做时记录原因、责任、工单和新承诺。 |
| 待退款、退件在途或已替换 | 可分别看到退件、替换件、重做与退款进度。 | 对照原支付流水、退款结果及退件签收。保留原订单物流事件，出现失败或金额不符进入财务待办。 |

### 4.4 运营工作台和权限

- **用队列管理今天要处理的单。** 首版支持按单号、状态、日期搜索，提供待验配、待补资料、临近超期、待发货、物流异常和退款滞留视图。每条记录含负责人、阻塞原因、承诺时间、下一动作和最近更新时间。试单可先用受控台账承接，交接时按订单号与后台互查。
- **至少明确四类职责。** 商品人员维护可售范围与价格。验配人员看到加工所需数据。客服能查订单、处理工单和发通知。财务能核对收款、审批和执行退款。现有后台使用统一管理员权限，订单详情包含处方、联系和交易字段，新增操作时应限定可见字段和权限。
- **保留变更原委。** 商品停售、改址、例外放行、退款、补发和重做记录操作者、时间、原因、前后值与关联单号。补充超期、付款异常、长期待退款、通知失败的告警承接人和值班方式。演练本班未结案、接班人接手和负责人临时缺席。
- **权限验收。** 用各类人员账号分别完成一张正常单和异常单。商品人员只看商品资料，验配人员看到加工所需信息，财务按退款字段完成核对。临时授权有申请人、批准人和结束时间。

[后台页面](../front_end/src/pages/AdminDashboard.tsx) · [后台接口](../backend/src/main/java/com/klarheit/backend/order/AdminController.java) · [后台访问配置](../backend/src/main/java/com/klarheit/backend/security/SecurityConfig.java)

人工处理时，可用同一条台账记录「付款完成后发现需要补瞳距」的演练。验配把订单改为待补资料，记录缺项与回复期限。客服通知用户并约定下次联系。用户提交后，验配确认版本和新交期，客服同步给用户，再进入制作。若用户选择退出且适用退款规则，财务核对原订单、退款金额及商户结果，客服确认反馈完成后结案。

## 5. 经营模型、用户验证与增长顺序

### 单单贡献和接单上限

- **单单贡献按真实订单计算。** 网关实收减已退款，再减实际发生的镜框、镜片、加工质检、包材、物流、支付费、售后变动成本及适用税费。实收已扣优惠，台账避免重复扣减。按订单分开记录已发生的重做和退回运费。获客成本按对应渠道实际新增付费用户计算，另看扣除获客成本后的贡献。固定开支另列。
- **按最慢的环节定上限。** 将合格库存可支持单量、验配、加工质检、发货、客服与售后的可承接单量换成同一周期口径，取最低值并留异常、补货和重做余量。某款缺货可以单独停卖。无法按期处理整批时暂停新单，优先给存量用户反馈。
- **后台销售额暂以运营参考使用。** 现有统计按当前处于已支付、已发货及已送达的订单金额汇总。每周另核实收、退款、净额和渠道成本，并和商户账单对齐。首轮用实际样本推算合理售价、可承受返工率和每单服务工时。 [后台统计实现](../backend/src/main/java/com/klarheit/backend/order/AdminController.java)

### 先验证用户任务，再投放

- 首轮建议找 5–8 位目标用户，用自己的手机从商品页走到测试支付、查单和售后。先问最近一次配镜如何选、付款和处理不适，再观察任务是否能独立完成、第一次卡在哪里、是否理解价格和交期。覆盖持处方、不确定缺哪项资料、拒绝摄像头和帮家人看款的人。
- 试单先从可回访的邀请用户或验配方导入。记录来源、设备、是否已有处方、是否试戴、是否中断及中断原因。试戴价值看它能否帮助用户确定某款和继续配置。用户访问后既可以直接选框，也可以先试戴。
- 发现新客主要卡在进入配镜后才遇到登录、填单困难或款式选择时，把对应改进排到 P1。跨设备草稿、多副合单及会员功能由实际需求决定。增加公开获客前检查商品链接能否分享、预览信息是否准确、下架后能否找到替代款。真实微信支付和门店预约分别依赖使用偏好与门店服务能力。当前预约页是占位，可先把交易路径里的入口收起来。 [预约现状](../front_end/src/pages/AppointmentsPage.tsx) · [站点入口](../front_end/index.html)

## 6. 实施顺序与发布门槛

| 阶段 | 交付和负责人 | 进入下一阶段的条件 |
| --- | --- | --- |
| ① 确定能卖的业务 | 项目负责人确认市场和模式，采购与验配签字确认可售商品、处方范围、样品、价格、加工和交期。客服与财务确认处理规则、对账及收款主体。 | 拿到可售清单、责任人、承诺和单单成本。若只具备镜架能力，先落实镜架独立成交。供货或客服未就绪时开放浏览和咨询。 |
| ② 串通演练环境 | 产品与研发完成款色、报价、登录恢复、订单和客服入口。运营按异常场景表演练，把需要人工处理的步骤记录到工作台。 | 移动端、中英文和核心键盘流程通过。正常与异常订单可逐笔说清状态、款项、库存和下一步。 |
| ③ 限量真实试单 | 财务验证一笔授权的真实小额付款和原路退款，验配、加工、物流、客服随后完成真实交付。运营按人员产能设置邀请量和接单量。 | 每笔交易与商户账单吻合，已送达单可核实签收，异常单皆有承接人。连续两批已到承诺时间的订单有可用数据再讨论扩大。 |
| ④ 按数据加量 | 由项目负责人和运营每周看交付、售后、成本和流失，明确下一次放量上限和首要体验改进。 | 下表指标达到预先约定的试运营门槛，且没有仍未解决的严重事件。出现触发条件时按停单流程处理。 |

### 试单验收场景

| 场景 | 通过条件 |
| --- | --- |
| 最短成交路径 | 用户从商品进入配镜，付款后在手机浏览器和另一台设备找到同一订单。商品、处方摘要、成交价、送达区间和通知一致。 |
| 款色下架与最后一件 | 历史链接、购物车和试戴页提示款色变更并保留可复用内容。两个尝试同时购买最后一件时，只有可交付的一单能继续。 |
| 参数缺失与付款后补材料 | 正常可配、不确定和无法加工各有分流。付费后进入补充队列能暂停制作，明确补充期限、退款选项和更新后的交期。 |
| 支付无法确认与重复提交 | 模拟弱网、取消回跳、延迟确认、刷新重试和退款失败。同一购买意图可追踪一笔有效订单，库存和优惠的扣减、释放与退款口径一致。 |
| 工厂延期、质检失败与物流丢件 | 用户收到更新后的进度和处理选择，后台能追到负责人、下一次联系时间和处理结果。记录延期承诺的历史，签收时间可核对。 |
| 发货后重做、退换与退款 | 用户从原订单发起，能看到原物流、新运单及退款进度。财务对得上金额，客服记录面向用户的解释及责任。 |
| 账号丢失和共享设备 | 验证手机号未绑定、收不到验证码、邮箱误填和登录过期时的恢复。退出后切换账号，看不到上一位用户的处方或截图。 |
| 摄像头和界面限制 | 用 iOS、Android 真机及桌面走查摄像头拒绝、权限撤回、模型加载和试戴退出。用中英文、窄屏、放大、读屏和键盘完成核心路径。 |
| 发布故障下停止新单 | 临时关闭新结账后，已付和在途订单仍能查询，支付回调、对账、退款与售后可继续。人员能按恢复步骤核对所有受影响订单。 |

### 指标、暂停与恢复

| 指标 | 定义与数据来源 | 试点门槛示例 |
| --- | --- | --- |
| 按期交付率 | 按首次承诺的送达时间归集到期已付款订单，其中按期签收的比例。另列用户主动取消、待补料、重做和交付失败，以及重新承诺后是否兑现。 | 示例为至少连续两批到期订单，按期签收达到 90%。样本较小时同步逐单回顾，列出分子与分母。 |
| 账实一致与订单积压 | 每笔已付和退款均能按订单号、商户流水和金额核对。每天看待确认、退款滞留、临近超期和无负责人的订单。 | 账实差异与无负责人的异常为零。已有负责人的差异也要先按约定时限消除再放量。 |
| 售后首次响应与重做 | 受理后在承诺时限内获得实质回应的比例。另列结案、重做比例、平均费用和主要原因。重做率按签收后经过同一观察时长的订单归集。 | 首次响应示例门槛为 95%。若量很小，逐单确认响应和处置。 |
| 任务完成与转化 | 商品详情 → 开始配镜 → 完成配置 → 创建订单 → 网关确认。按来源、设备、试戴及处方情况分组。 | 先建立基线。支付成功从服务端订单与网关去重。核心任务在用户测试中可独立完成，反复出现的阻断已修复。 |
| 单单贡献 | 按净实收和实际变动成本计算，再看获客后的贡献。纳入运费、重做和辅助下单的实际投入。 | 由负责人结合试单预算确认最低贡献，明确是否可加量及原因。 |

## 8. 评审把关补充与实施落地记录

### 8.1 代码级把关新发现的 12 项高危遗漏

对照当前工作区代码核查后，除前文 1–7 节提出的问题外，还发现了以下原评审未覆盖但会直接导致资金、合规或核心转化故障的缺陷：

1. **支付宝回调缺少 `app_id` 校验且忽略 `TRADE_FINISHED`，微信 XML 分支跳过金额核对并错误回退 `callbackSecret`**（`PaymentCallbackController.java`）。
2. **超时对账并发关单回查 (`recheck`) 漏检 `paidAmount` 金额一致性**（`OrderService.java`）。
3. **零元订单未拦截（支付宝拒单）且未校验“必选且仅选 1 款基础镜片 (`category=LENS`)”**，导致只买镀膜无镜片的非法订单可通过结算（`OrderService.java`、`ConfigLab.tsx`、`Checkout.tsx`）。
4. **商品删除后历史订单查询 NPE**：`getMyOrders` 依赖 `product.getName()` 而非 `productNameSnapshot`；且 `lensOptionsSnapshot` 默认为空列表 `[]`，判空分支失效。
5. **共用设备退出登录隐私泄露**：`AuthProvider.logout()` 未清理购物车处方与试戴截图；刷新恢复会话时也未调用 `setUserContext()`，导致归因断链。
6. **导航致命路径错误**：`Navbar` 中“我的订单”跳往 `/checkout` 而非 `/my-account`，且移动端抽屉菜单完全缺失购物车入口。
7. **确认邮件币种与交付周期失真**：`EmailService` 写死美元 `$%s`、14 天制作期与“Swiss Precision Eyewear”口径，且未对用户输入做 HTML 转义、缺少发货通知邮件。
8. **支付宝下单未传 `timeout_express=30m`**：与后端 30 分钟超时调度错位；另需在试运营前实测确认移动端是否需要补充 `AlipayTradeWapPayRequest`（当前为电脑网站 `PagePay`）。
9. **生产安全与 CSP 冲突**：`SecurityConfig` 在 `prod` 环境未限制 Swagger/OpenAPI 访问；`nginx.conf` 放行未使用的 `api.resend.com` 却拦截 GA4；`AdminDashboard` 图片报错回退到外部 Unsplash URL 触发 CSP 报错。
10. **结算页竞态与优惠券漂移**：异步 `fetchAddresses()` 会覆盖用户已手动输入的收件人/地址；切换镜片后旧优惠券金额不自动失效；401 重新登录丢失处方/镜片/finishId；存在 `color.matte-black` 键名不匹配与硬编码 `"Remove"`。
11. **订单详情时间线缺失 `PENDING_PAYMENT` 且缺少客户自助恢复入口**（继续支付 / 刷新支付状态 / 制作前取消 / 售后与改址开票工单）。
12. **个人资料页多处假数据与死按钮**：处方卡硬编码 `—`、硬编码“邮箱已验证”、修改密码与注销账号按钮无响应。
